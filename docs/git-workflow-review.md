# Git workflow review — 9 October 2026

This review follows a worktree session from the review panel through the API, session lifecycle, squash merge, and startup cleanup. It also checks nearby branch-switch, refresh, pull, and workspace-removal operations. The implementation keeps user work recoverable and makes the merge destination and required steps visible.

## Findings addressed

| Priority | Finding                                                                                                                                                                                                                | Resulting behavior                                                                                                                                                                                                                                                                                                              |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1       | Successful squash merges force-removed the source worktree and deleted its managed branch. Ignored files and the original commit history could disappear. Startup cleanup could also remove retained merged worktrees. | Merging retains the source worktree and branch, including ignored files. Startup protects merged sessions. Explicit session deletion remains the cleanup boundary.                                                                                                                                                              |
| P1       | Commit failures during host squash merges invoked `reset --hard`. Recheck source/destination state before applying it. Fast-forward an occupied destination, or update an unoccupied branch with an expected-old-commit check. No destructive destination rollback. Failed preparation is retained and its path appears in the error. |
| P1       | Ignored files can collide with incoming tracked paths. Git's merge overwrite flag alone did not protect the non-fast-forward source case in the regression test.                                                       | Explicitly check ignored-file and directory collisions before merging, switching, refreshing, or pulling. Refuse the operation and identify the path instead of overwriting it.                                                                                                                                                 |
| P1       | A staged conflict resolution allowed additional unstaged/untracked edits through finalization. The old cleanup then removed them.                                                                                      | Require all resolutions and other edits to be staged or committed before continuing. ## Expected interaction

1. Review the changes and select **Merge session…**.
2. Choose any existing local destination branch. The session’s base branch is the initial default, and the source branch is excluded. Read the source branch, destination checkout, and readiness result. Dirty destination files, missing refs, unfinished Git operations, and ignored-file collisions block the action with a recovery instruction.
3. When needed, **Commit all and merge** commits staged, unstaged, and untracked project files before finalization. The count and inclusion rule appear before the action. A failed merge after that commit explicitly says the changes were committed.
4. For known conflicts, **Prepare conflict resolution** puts the merge in the source worktree. Resolve the files using the existing review/editor flow, stage each resolution, and retry. The destination remains unchanged until a successful commit can be applied.
5. A merge that hits conflicts remembers its chosen destination for retries and prevents destination changes during a pending resolution. The success state names the destination, explains that the source is retained, and reminds the user to push the destination separately to publish the local merge.

## Operational boundaries

- Retained source/preparation worktrees consume disk space. Source worktrees are removed by explicit session deletion; failed preparation paths remain available for recovery.
- Commit hooks execute inside the temporary preparation worktree. Hooks that require dependencies or local configuration present only in the original checkout can fail. Hooks are not bypassed; failures retain source/prepared work and report the preparation path.
- The app rechecks Git state before applying changes. External tools do not share its in-process repository lock; this is not a transaction across arbitrary external filesystem writers or multiple processes.
- Git merge previews compare committed history. If Commit all adds new content, the actual merge rechecks that content and may discover additional conflicts.
- Merge conflict editing uses the existing file review/editor flow; this change does not add a three-way conflict editor or remote push automation.
- Explicit deletion and file-discard controls remain destructive user actions. This audit does not claim every Git, hook, external-tool, or filesystem failure is eliminated.

Git reference behavior: [worktree removal](https://git-scm.com/docs/git-worktree.html) and [merge-tree output and exit status](https://git-scm.com/docs/git-merge-tree/2.50.0.html).

## LLM metadata generation follow-up

Reviewed the local t3code implementation, especially `packages/provider-core/src/server/textGenerationPrompts.ts`, `apps/server/src/git/GitManager.ts`, and the Codex/Claude text-generation adapters. Adopted its bounded Git context, concise structured output, separate commit/PR scopes, committed PR templates, and short-lived generation requests. Agentctl uses its existing ACP provider interface instead of assuming a particular CLI.

- **Commit:** Generate message creates an editable subject/body from the selected scope. Clicking Commit or Commit and push with a blank message generates it first; manually entered messages bypass generation. Staged-only selection excludes unstaged and untracked files. Include unstaged includes all nonignored pending files without staging them during generation. A provider failure stops the action and retains the editor.
- **Merge:** Generate message describes cumulative session changes against the selected local destination, including pending nonignored files. The generated message is editable. Leaving it blank retains the existing session-message fallback, so merging does not depend on provider availability.
- **PR:** Generate title & description compares committed HEAD against the merge base of the selected destination. Prefer its tracked remote ref when available; do not fetch implicitly. Dirty local edits and base-only commits are excluded. The committed repository template is included when present. Generated testing claims must say Not run unless evidence is supplied. Review and publish remain separate actions.
- **Provider:** By default, reuse the session provider profile and selected model, with low reasoning effort for these short tasks. Start a new ACP session in an empty temporary directory, with no app MCP servers or additional repository directories; deny permission and elicitation requests. Close the helper and remove its directory on success or failure. Requests time out after two minutes. This does not append to the user's session conversation. ACP providers can retain their own helper-session history; their native tool and sandbox behavior remains provider-specific.
- **Draft safety:** Validate output shape and size. Reject requests overlapping for the same session. Re-read the Git scope after generation and reject stale results when source files, index, HEAD, or destination changes. Ignore late UI responses after closing, changing the destination/scope/session, or editing the draft. Preserve PR fields across closing/reopening, and guard duplicate publication.

Generation tests use temporary Git repositories and fake ACP responses. Live authenticated provider quality and latency were not exercised. Large patches are bounded and marked as truncated; very large Git command output can fail safely instead of generating an incomplete draft. Provider-native tools are not an OS sandbox: app permission requests are denied, the real repository is not the helper working directory, and the generation prompt explicitly requires no tools.

TypeScript builds, scoped lint, formatting, architecture checks, and diff whitespace checks passed. ## Dedicated generation provider and model settings

Settings → General → **Git text generation** now lets users choose a dedicated installed, enabled provider/profile and one of its advertised or custom models for commit, merge, and PR drafts. The default **Use session provider and model** preserves the earlier behavior; selecting **Provider default** uses the chosen profile’s default model. These preferences apply to all projects and persist in the existing server settings store as one provider/model object. Selecting another provider resets the model choice to that provider’s default in the same save.

The API validates the provider/model pair before writing any settings. Generation resolves this override without changing the chat selection, and uses the chosen profile’s launcher/environment. Unavailable, disabled, hidden, uninstalled, unauthenticated, and removed-model choices produce an actionable error instead of silently using another provider. The UI keeps stale selections visible, retains the previous saved selection on failure, and locks both controls while saving.

Reference: t3code’s provider-instance model picker and persisted text-generation/source-control model selections in `apps/web/src/components/settings/SettingsPanels.tsx` and `packages/contracts/src/settings.ts`. Agentctl keeps one Git-specific setting for all three draft types.

TypeScript builds, scoped lint, architecture, formatting, and diff checks passed. ## Actions row redesign

The review header separates scope/display/staging controls from a dedicated Git workflow row. Four labeled controls replace the ambiguous split button: Commit, Sync, Merge/Finish, and Session. Sync contains only fetch, pull, and push with tracking information; Session contains branch selection, PR creation/opening, and a separated discard action. Merge is no longer duplicated in a dropdown.

Commit opens a focused form with a message editor, generation action, file scope, and one primary submit button. Push after committing is an explicit checkbox; push/pull/fetch and base-branch preferences no longer crowd the default commit form. Existing push safeguards and error reporting remain active. Sync can close during a network request; progress and failures remain visible below the action row. The controls adapt to panel width and larger text using container queries.

Validation: 52 UI tests across four related files, TypeScript, scoped lint, formatting, and architecture checks passed. Isolated browser checks covered 320-pixel panels, enlarged text, the three-action Session menu, the focused Sync menu, and commit form layout without running real Git operations.

## UI consistency and cleanup — 14 October 2026

Commit, PR, and Merge now share a bounded dialog body, fixed footer, Octicons header, message editor, generation button, and accessible error/status notices through `GitDialog.tsx`. PR actions remain reachable in small windows; the publishing state immediately locks fields and prevents duplicate submissions and dismissal. Generation remains separate from publication, and manual PR drafts remain editable during generation with stale-response protection.

- A successful commit followed by a failed push now offers **Retry push**, preserving the local commit and avoiding another commit even after file counts and the message reset. Publishing from Sync clears this recovery state too. New pending files can be committed through **Commit more changes**.
- Commit progress distinguishes generation, committing, and pushing. Sync failures remain visible after closing/reopening the popover; successful fetch, pull, and push display clear feedback.
- Merge retains its destination and message across closing/reopening, displays actual progress during submission, and continues to recheck readiness after failures. Its source label comes from the actual Git checkout rather than a stale session branch label.
- PR handles a detached source or unavailable Git remote with actionable guidance. Errors use the same notice styling as Commit and Merge; reopening clears the previous publication error while keeping the fields.

Browser verification exercised Commit → push failure/retry → fetch failure/retry → pull failure/retry → PR generation/editing/publication failure/reopen/retry → Merge selection/editing/reopen/failure/retry. It used the real components with simulated operations only, including 320 × 480 checks, long branch names, and a single commit followed by two push attempts. No live GitHub PR, authenticated generation request, or user repository mutation was performed. Temporary preview files and the preview server were removed.

Validation: the complete browser project passed **489 tests across 90 files**; the affected Git/API suite passed **204 tests across 18 files**. Workspace-wide typechecking, scoped lint, formatting, architecture, and whitespace checks passed. Additional focused recovery tests cover push-only retries after refreshed file counts, publication through Sync, PR draft retention and immediate pending state, detached PR heads, retained merge destinations, and merge retries after partial success.
